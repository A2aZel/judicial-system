# Подготовка пар `rostov` / `7kas`

Локальный, детерминированный этап проверки полных пар «приговор первой инстанции → апелляционный или кассационный акт». Pipeline не меняет processed dataset/index: включение выполняется отдельным `build_training_dataset.py` после проверки lead и повторной проверки SHA.

## Входы и выходы

Основные входы:

- `corpus/regional/raw/collection-2026-11-10/unified-case-index.jsonl`;
- `corpus/regional/raw/collection-2026-11-10/metadata.jsonl`;
- локальные тексты, raw-файлы и официальные доказательства идентичности по путям из индекса.

Результаты записываются только в этот каталог:

- `pair-status.jsonl` — приватный постатусный журнал с реквизитами, артефактами и SHA;
- `summary.json` — агрегированные счётчики;
- `report.md` — только агрегаты, без персональных данных, реквизитов дел, UID, URL и хешей;
- `README.md` — метод и порядок возобновления.

## Метод

1. Отбираются все записи источников `rostov` и `7kas`, без ограничения `--limit`.
2. Для каждого основного документа заново вычисляются SHA256 текста, raw-файла и доказательства identity. Проверяются полнота текста и официальный статус identity.
3. Второй акт ищется только среди локальных записей с общим официальным ключом `first_case:суд|полный_номер` и той же датой приговора. Слабые ключи и самостоятельно выведенные перенумерации не используются. Если у обоих документов есть формальные UID, их пересечение обязательно.
4. Дополнительно проверяются полные приговоры локального СудАкта: тип и номер в метаданных, суд, номер и дата в полном тексте, длина по метаданным, мотивировочная и резолютивная части. Принимается только однозначное совпадение. Для таких приговоров исходный HTML не сохранён; SHA текста и файла метаданных проверяются, а ограничение `text-only provenance` учитывается отдельно.
5. `verdict_group_id` учитывает официальные ключи исходного дела, дату и тип приговора. Разные апелляционные события с одинаковым UID не объединяются: в событии также учитываются дата, тип и нормализованный текст.
6. Подтверждаются только независимые полные тексты `trial_verdict` и `appeal_against_verdict` / `cassation_against_verdict` / `cassation_on_merits_appeal`. Цитата приговора в более позднем акте вторым текстом не считается. Процессуальные акты, апелляционные приговоры и кассации таких новых приговоров отклоняются.
7. Текстовые проверки повторяют строгие принципы существующего `verify_pair`: длина, тип акта, суд, даты, номер или официальное доказательство его связи с документом, отсутствие противоречий UID и хронологии.
8. `outcome` извлекается только после последнего маркера резолютивной части. Поддерживаются `unchanged`, `changed`, `cancelled`, `remanded` и `unknown`. `remanded` обозначает отмену апелляционного акта с новым апелляционным рассмотрением без прямой отмены приговора. Просьбы сторон в мотивировке исходом не становятся.
9. `missing_sentence` / `missing_appeal` и `identity_errors` независимы: отсутствие второго локального текста не скрывает предупреждения о реквизитах имеющегося акта. Статус `identity_failed` относится к найденной комбинации двух текстов, не прошедшей проверку.

## Сеть и разрешённые документы

Новые запросы к карточкам и документам не выполнялись. Официальные `robots.txt` обоих источников содержат запрет `/*name=sud_delo`; поэтому прямые ссылки на карточки и документы этих сайтов не являются разрешёнными для данного этапа. `/search`, поисковые выдачи и обход robots/CAPTCHA не использовались. Две проверки `robots.txt` были выполнены последовательно с паузой 4 секунды; CAPTCHA не возникла. Число сетевых запросов к судебным документам — 0.

Если lead позже предоставит уже скачанные официальные документы, их можно передать отдельным индексом той же схемы через `--extra-index`. Скрипт ничего не скачивает и не меняет исходную коллекцию.

## Запуск и resume

Из корня проекта:

```bash
# Однократно зафиксировать независимые SHA существующих текстов СудАкта.
python tools/prepare_rostov_7kas_pairs.py fingerprint-sudact
python tools/prepare_rostov_7kas_pairs.py run
python tools/prepare_rostov_7kas_pairs.py run --resume
python tools/prepare_rostov_7kas_pairs.py run --resume --extra-index /полный/путь/к/related-index.jsonl
python tools/prepare_rostov_7kas_pairs.py report
```

`pair-status.jsonl` атомарно перезаписывается после каждого обработанного кандидата, поэтому прерывание не оставляет частичной JSONL-строки. Обычный повторный запуск заново проверяет всё. В режиме `--resume` прежний `confirmed_pair` reuse’ится только при совпадении `processing_contract`, пересчитанного outcome, SHA обоих текстов и доступных raw-файлов и отсутствии текущих ошибок identity. Это позволяет обнаружить второй акт после добавления нового локального индекса и не сохранить устаревший outcome после изменения parser.

Для СудАкта `text-sha256.json` является отдельным сохранённым эталоном: подготовка пар не вычисляет новый эталон из изменённого TXT. После ручной проверки обновления источника эталон пересоздают явной командой `fingerprint-sudact`. Суд, номер и дата сверяются в первых 2500 символах приговора, а не по упоминанию в исторической части.

Дополнительные индексы используются только как репозиторий вторых актов и не увеличивают число исходных кандидатов `rostov` / `7kas`.

## Проверка

```bash
python -m pytest tests/test_prepare_rostov_7kas_pairs.py -q
```

Тесты полностью синтетические: полные пары, SHA/UID-конфликты, официальные алиасы, разные события с общим UID, точные дубликаты, отсутствующие акты, процессуальные документы, новые приговоры и outcome по резолютивной части.

`pair-status.jsonl` содержит реквизиты и потенциальные персональные данные. Хранить локально, не коммитить и не публиковать.
